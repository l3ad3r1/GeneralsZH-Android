# 2026-07 Development Diary

## 2026-07-30 — TCL NXTPAPER reaches the main menu through SwiftShader

Worked alongside the Gemini implementation lane on the TCL NXTPAPER 9469X
(Helio G99 / Mali-G57). The device probe confirmed two native-driver blockers:
Vulkan is capped at 1.1.177 and BC/DXT texture compression is unsupported, while
the current DXVK 2.6 build needs Vulkan 1.3 and the game data uses DXT textures.

The SwiftShader proof-of-concept now clears both blockers and renders the Zero
Hour main menu at the tablet's native 2200x1440 landscape size. This is real
on-device progress, but not a release yet: the animated menu was roughly 1 FPS,
the experimental SwiftShader fork still contains capability workarounds that
need narrowing, and a skirmish/soak pass has not been completed on the TCL.

Verified the latest proof APK offline:

- APK Signature Scheme v2/v3 passes.
- Signing certificate SHA-256 is
  `b82277491a6e25094ab2521b32e7728f4e9eb165cb950f544badfcf4564a5374`,
  matching the certificate already installed on the TCL, so an update install
  should preserve GameData.
- All native libraries are 16 KB ZIP-aligned.
- `libvk_sw.so` is bundled and DXVK's Vulkan loader target is patched to it.
- APK SHA-256 is
  `5955c885976d24aa47bc8a114b8025a0de22f23148b2401463e40a244fde2f5c`.

The tablet was then connected and the verified APK was installed with
`adb install -r`, preserving the existing package data and GameData. SwiftShader
created its Vulkan instance and device, the engine completed initialization,
entered `GameEngine::execute()`, and rendered the main menu after a long first
shader warm-up. No fatal signal or Android crash-buffer entry was observed.

The UI was driven through SDL's touch path as far as Solo Play, difficulty
selection, and the "Choose Your General" screen. Rendering is correct enough to
navigate, but software Vulkan currently sustains only about 5-8 FPS at the
forced 2200x1440 backbuffer, so this is a running technical preview rather than
a comfortably playable build.

Fixed the incorrect TCL colors in the custom SwiftShader Android presentation
path. SwiftShader advertises a `B8G8R8A8` swapchain image, but the hand-written
`ANativeWindow` presenter locks `WINDOW_FORMAT_RGBA_8888` and previously copied
the bytes unchanged. Swapping red and blue during the row copy restores the
blue Zero Hour logo, blue UI/team colors, natural terrain, and orange
explosions. The corrected APK was update-installed with the same certificate
and held about 6.3 FPS during the verification soak with an empty Android crash
buffer, so the conversion introduced no material performance regression.

Added and applied reversible TCL profiles under `android/config/`. The original
device files remain beside them as
`Options.ini.before-swiftshader-tuning-20260730` and
`SagePatch.ini.before-swiftshader-tuning-20260730`. Texture/effect reduction
applied, but the mobile bootstrap overrides `Resolution = 1100 720` with native
dimensions, and the attempted `ShellMapOn = No` override did not disable the
animated shell map in this binary. A real lower-resolution backbuffer is now
the highest-value performance fix.

## 2026-07-30 — Native Mali legacy-DXVK path reaches the game

Built a second renderer lane for the TCL's Vulkan 1.1.177 Mali-G57 MC2 driver
using DXVK Native 1.9.2b, an SDL3 Android WSI port, and a 64-bit-safe
`d3d8to9` frontend. This avoids modern DXVK 2.6's Vulkan 1.3 requirement.

The first real-device D3D9 gate exposed five features the old frontend treated
as mandatory even though Generals does not require all of them:
`textureCompressionBC`, `fillModeNonSolid`, `multiViewport`,
`shaderClipDistance`, and `shaderCullDistance`. Requesting only supported
values allowed `vkCreateDevice` to succeed. DXT1, DXT3, and DXT5 remain
unavailable through D3D8/9, intentionally activating the engine's existing DDS
software decode path before RGBA texture upload.

Measured on the TCL at its full 2200x1440 surface:

- D3D9 clear/present gate: 59.8 FPS after fixing a persistent
  `VK_SUBOPTIMAL_KHR` swapchain rebuild.
- D3D8-to-D3D9 clear/present gate: 286.3 submitted FPS with mailbox present.
- Actual Zero Hour animated main menu: stable 29-30 FPS, up from roughly
  5-8 FPS through SwiftShader.

The first full-game run also found and fixed an Android-specific `d3d8to9`
gap: without the legacy D3DX runtime, `CopyRects` could not upload the
A4R4G4B4 dynamic font atlas, leaving menu labels blank. A lock/copy/unlock
fallback now handles the engine's full-surface atlas upload. The final device
screenshot has correct colors, textures, icons, and text while DXVK reports
the real Mali device and Vulkan 1.1 driver.

The hardware APK is `GeneralsZH-TCL-Mali.apk`; the earlier SwiftShader APK
remains the compatibility fallback. Full skirmish and lifecycle soak testing
is still required before calling the Mali lane release-ready. The signed APK's
SHA-256 is
`b2d5de434ae9eea751210dcf0cc1c5451aa74f86f76d860196d0d7816e37a2e4`.

## 2026-07-06 — Android tablet port, scaffolding landed

Started the Android tablet port today. The repo already ships a real iOS/iPad
port (~2,200 lines, fully playable per the playbook), so the smart move was to
treat that as the template rather than start from scratch. Research first,
then implementation.

### Research verdict
The single load-bearing question was: **can DXVK (D3D8→Vulkan) run natively on
Android?** It has never been built for Android upstream (doitsujin closed #1183
with "No" — but that was about Wine/emulation, not native linking). The native
non-Wine path is the same one the game already uses on Linux and iOS. Verdict:
**feasible but unproven** — the build blockers are concrete and patchable (gate
`-msse` behind x86; the aarch64 NEON bitops already exist), but the runtime gate
(driver quality) can only be answered on hardware. No Plan B exists, so it must
be spiked before committing the full budget.

Everything else (SDL3, OpenAL/Oboe, touch, deps, packaging) has a known path.
The strongest finding: **11 of the 17 iOS-guarded engine blocks port by simply
widening the `#ifdef`**, including the entire ~230-line touch gesture state
machine — the highest-effort iOS work.

### What landed today
- Introduced a `SAGE_MOBILE` macro (iOS ∨ Android) and widened the platform-
  agnostic mobile code to it: touch gesture machine, lifecycle render-gate,
  high-DPI drawables, `-xres/-yres` aspect matching. iOS-only mechanisms
  (MoltenVK, `funopen`, bundle paths) stay on the narrower `TARGET_OS_IPHONE`
  guard.
- Android bootstrap in `SDL3Main.cpp`: chdir to internal storage (the VFS analog
  of iOS's bundle GameData), portable stderr→file sink via `dup2` (bionic has no
  `funopen`), DXVK cache path.
- DXVK Android build groundwork: `Patches/dxvk-android.patch` (gate `-msse` behind
  x86 + high-DPI WSI fix), `cmake/meson-android-aarch64-cross.ini.in` (NDK
  cross-file), `cmake/dx8.cmake` Android branch (Meson ExternalProject →
  `libdxvk_d3d8.so`/`libdxvk_d3d9.so`).
- `android-vulkan` CMake preset + `arm64-android` vcpkg triplet.
- `android/` Gradle project (build.gradle with `externalNativeBuild` → repo-root
  CMakeLists.txt, AndroidManifest, GameActivity SDLActivity subclass).
- `scripts/build/android/package-android-zh.sh` + `stage-fonts.sh`.
- `PHASE06_ANDROID_PORT.md` and this diary entry.

### Honest status
**Scaffolding complete; runtime unverified.** No APK has been built or run on a
device yet. The DXVK-on-Android runtime spike is the explicit next gate — if a
d3d8 clear renders via DXVK on a real Android Vulkan driver, the port is viable
and the rest is performance/packaging work. If the driver can't give DXVK the
extensions it queries, the port is blocked (no fallback translator exists).

The Android tooling is all present locally (NDK r27, SDK API 35, an arm64-v8a
AVD, JDK 17, Gradle), so the spike can run as soon as there's a device or the
emulator's Vulkan support is confirmed.

## 2026-07-30 — TCL NXTPAPER (Mali GPU) tablet: SwiftShader breakthrough

Resolved the exact risk flagged as open at the end of the 07-06 entry above: *"GPU
driver fragmentation: Mali vs Adreno Vulkan drivers vary widely."* They do — badly.

### The problem
Same codebase, second device: a TCL NXTPAPER tab (MediaTek MT8781, ARM Mali-G57). The
engine boots fully and dies at D3D device creation. A native Vulkan probe run directly
on the device (not trusting Android's feature-flag layer) found two hard blockers:
Mali's driver caps at **Vulkan 1.1** (DXVK needs 1.3), and Mali has **zero BC/DXT
texture support** — a permanent hardware limitation, not something a driver update
could fix, and Generals ships DXT-compressed textures throughout.

### The fix
**SwiftShader** (software Vulkan) clears both blockers in one move — Vulkan 1.3 in
software, plus software BC decode. Substituted into DXVK's runtime `dlopen` target via
the same binary-patch technique used throughout the Android stabilization work
(swap the `"libvulkan.so"` string for a same-length replacement), no rebuild required.

### Five things that had to break before it worked
1. `adb push`-created GameData wasn't group-readable by the app (`chmod -R 777` fixed
   it) — this was misdiagnosed upstream as a data-compatibility problem and cost real
   time chasing a nonexistent "Android needs different game data" theory before the
   actual (much smaller) permission bug was found.
2. SwiftShader deliberately doesn't advertise `VK_KHR_swapchain` on Android — it
   expects the Android Vulkan loader to supply it over `VK_ANDROID_native_buffer`,
   which a direct `dlopen` bypasses. Un-guarded two `#ifndef __ANDROID__` blocks in
   SwiftShader's own source to expose it directly; the implementation was already
   compiled in, only the advertisement was suppressed.
3. `vkCreateDevice` returning `-8` (`VK_ERROR_FEATURE_NOT_PRESENT`) — DXVK wants
   several Vulkan11/12/13 feature bits SwiftShader's base query doesn't report; fixed
   with targeted capability mocks.
4. A binary patch pass **inserted** a byte instead of overwriting one, silently
   shifting every ELF offset after it and breaking `dlopen` outright — and, worse,
   knocking the earlier double-free NOPs out of alignment so they stopped working
   too. Caught via file-length + NOP-alignment comparison against a known-good build.
   Every patch must be length-preserving; pad with NUL, never grow the file.
5. A false `nullDescriptor = VK_TRUE` mock (SwiftShader has no null-descriptor support
   at all) caused DXVK to correctly write a null buffer handle, which SwiftShader then
   dereferenced. The general lesson: prefer reporting a capability **false** and
   letting DXVK use its own fallback over reporting **true** and hoping — DXVK is
   built for exactly this kind of hardware variance; a software Vulkan implementation
   generally is not a superset of everything DXVK might ask for.

### Result
The main menu renders — correct terrain/water shading, correctly BC-decoded textures,
correct fonts, full menu — at native 2200×1440 landscape on hardware the shipped
build cannot run on at all. Confirmed by screenshot, not just a clean log (with several
capabilities falsely advertised at various points, "no crash" was repeatedly *not* the
same as "renders correctly").

**Honest status**: proof of concept, not shippable. ~1 FPS at the menu on this
software rasterizer — expected, not a bug, and skirmish/campaign performance is
untested. The SwiftShader source patch lives in a local working tree, not yet
upstreamed. Full writeup: `docs/WORKDIR/phases/PHASE07_TCL_SWIFTSHADER_PORT.md`.
Roadmap tracked on the project wiki.
